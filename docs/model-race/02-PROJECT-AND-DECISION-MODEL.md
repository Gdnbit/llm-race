# 02 · 项目理解、节点发现与多目标决策模型

> **设计规范草案。** 本文强调如何制定评测，而不是预置一组固定模型分数。

## 1. 项目感知的入口与生命周期

入口应是**当前开发工作区**，而非先询问用户“想测哪个模型”。Skill 获取并记录（只读、获授权、范围可配置）：

- **开发阶段**：只有 PRD/设计？初版 MVP？已有模型调用/单测？有已标注业务数据？已在运行、有 Trace 和稳定基线？有生产约束？
- **业务目标**：输入是什么、最终可验收输出是什么、使用频率、单次成功任务的业务价值、错误后果、人工复核角色。
- **软件事实**：源代码、已有模型配置、路由、API/SDK、Prompt、编排 DAG/状态机、运行环境、缓存和现有兜底、测试、CI、现有报告。
- **资源与限制**：预算、国家/数据位置、网络可达性、依赖版本、CPU/GPU/RAM、响应时间门槛、供应商白名单与禁止项、许可、合规与运营限制。
- **数据条件**：是否已有足够的真实且可合法用于评测的已标注案例；分布是否覆盖长尾和失败情况；允许本地处理还是允许外部模型 API。
- **不确定性**：尚未提供哪些信息，哪些可以从代码和样本推测，哪些必须向用户确认；不能将推测伪装成确认事实。

根据成熟度自动切换运行策略：

| 状态 | 策略 | 证据边界 |
| --- | --- | --- |
| 需求/文档阶段 | 提出节点草图、硬约束、候选技术路线、需收集的样本和评测计划 | 不可报告“本项目已实测” |
| 部分实现 | 静态扫描、定位模型调用、用单测与合成/部分业务样本测候选 | 明确样本稀少与接口变更风险 |
| 可运行 MVP | 获取基线、独立节点 A/B、系统回归与小规模压测 | 不推断生产 SLA |
| 生产运行 | 在许可范围内用抽样 Trace/人工标注评测，分析峰值与失败分布，先影子验证 | 不做未审核的在线配置切换 |

## 2. 节点发现方法（Project Discovery）

### 2.1 多通道证据

1. **静态代码**：SDK 调用、HTTP 服务商客户端、模型名环境变量、模型路由器、工具/函数调用、工作流编排、OCR/语音/图像库、Prompt 模板、Embedding 向量调用。
2. **架构与文档**：PRD、API contract、diagram、README、ADR、待办、需求验收条件；从“待实现节点”与“已运行节点”分开抽取。
3. **测试/运行证据**：集成测试、请求样例、OpenTelemetry/Trace（须脱敏）、测试运行、依赖图、错误日志。静态扫描发现不到的动态节点可能由 Trace 补足。
4. **人工轻量确认**：不可准确判定的私有云工作流、配置注入、外部 Agent、Shadow API 等标注 `needs_review`。

### 2.2 节点登记契约（建议）

每个 node 至少记录：

| 字段 | 内容 |
| --- | --- |
| `node_id` | 稳定 ID，重复扫描可对比差异 |
| `status` | planned / detected / verified / deprecated |
| `evidence` | 文件路径/行号、流程文档、追踪示例；证据可信度 |
| `task` / `modalities` | OCR / ASR / text extraction / reasoning / text-to-image 等；输入输出模态 |
| `current_implementation` | 当前模型/方案/Provider/部署方式/Prompt 版本；未找到可为 null |
| `input_contract` / `output_contract` | 类型、大小、语言、质量、格式、错误处理、要求结构化程度 |
| `upstream` / `downstream` | 上游输入来源、下游依赖，故障传播与 fallback |
| `constraints` | 禁止出境、最大预算/延迟、最低质量/许可证/硬件 |
| `datasets` | 已有测试、生产匿名样本、人工真值、公开候选数据集 |
| `coverage` | 发现置信度及未覆盖位置 |

**注意**：不应把所有 OCR/LLM 调用按模态合并成一个节点；“同一模型在不同业务环节”仍可能有不同测试和优先级。

## 3. 逐节点需求诊断

一个推荐决策不是固定的“质量 40%、速度 30%、成本 30%”，而是先作**任务风险分析与价值分析**。每个节点都回答：

- **目标**：要输出什么可验收结果？哪些错误可自动纠正，哪些错误会触发高风险后果？
- **输入数据分布**：实际比例和难点，包括语言、字段密度、文档类型、长度、图像质量、扫描倾斜、噪点、背景、音频噪声/口音、并发峰值、易混淆实体。
- **流程角色**：关键阻塞步骤或异步后台处理？中间输出是否人审？低概率失败是否导致全链路失败？
- **部署约束**：本地 vs 云端、CPU/GPU/RAM、设备功耗、容器/移动端/边缘、区域/合规、离线、网络波动。
- **提供商与许可证**：闭源 API、开放权重、自托管、商业许可、上下文长度、输入限制、结构化输出/工具调用等是否必需。
- **资源约束**：测试费用及计算资源；生产请求频次、吞吐与 P95 延迟、供应商配额、运维人力。
- **质量指标**：以用户业务目标选用最有意义的指标；例如字段准确率、拒答准确率、违禁写入率、WER/CER、图像遵循度；不将所有指标混为一个数。

### 3.1 三层决策标准

**A. 硬约束（先筛）**：不可泄露数据、不可使用某种云部署、许可禁止、无法处理目标输入模态/语言/文件尺寸、硬件不可达、预算/最大延迟不可接受、达不到必要安全门槛等。**未核实**不代表满足。

**B. 优化指标（按节点选）**：业务任务成功率、错误成本、单位成功任务总成本、推理/首包/P95 延迟、吞吐、稳定性、质量下界。避免用主观加权分代替合格门槛。

**C. 生命周期指标（长期）**：支持周期、API 变更、厂商锁定、迁移代价、部署维护、许可证风险、可观测性、回滚难度、模型更新后回归责任。

## 4. 候选方案空间（不限于模型）

候选可以是：

- 传统规则、正则、搜索/数据库查询、已有 SDK；
- PDF 原生文本提取、OCR 专用引擎、文档理解模型、VLM 端到端；
- 小模型/大模型、开源权重自托管/闭源 API、多阶段流水线；
- 固定单节点方案、缓存、批处理、质量检测、动态路由、重试、人工复核；
- 组合实例：可解析 PDF → 直接提取；普通扫描 → 轻量 OCR；模糊财务表格 → 文档专用模型；高风险低置信度 → 人工验证。

**必须将路由器本身的误判、额外延迟、训练/维护及回退成本计入评测。** 条件式路由只是候选方案，不默认比静态配置好。

## 5. 一次生成多套有意义的系统方案

建议最初允许以下目标模板，由 Agent **按项目动态启用/合并/删去**：

| 模板 | 优化方向 | 不可牺牲 |
| --- | --- | --- |
| quality-first | 业务任务成功率/严重错误率 | 既定安全、许可、最小可接受成本上限 |
| speed-first | P95 端到端延迟、首包与吞吐 | 最低业务质量 |
| value-first | 达到质量门槛后最小化每合格任务成本 | 质量、安全/可靠性约束 |
| privacy/on-prem | 私有化、数据边界、无网部署 | 本地可运行性与质量底线 |
| open-weight | 可用开放权重、部署可控性 | 许可证合法性和硬件能力 |
| reliability-first | 多提供商回退、稳定性、恢复时间 | 数据边界与预算 |
| hybrid-optimal | 不同节点混合云/本地/传统算法 | 业务链完整性与运维可承受性 |
| low-TCO | API + 人工 + 服务器 + 运维长期总成本 | 最小验收标准 |

“质量优先”与“开源优先”可能成为组合约束；不是一定输出八套名字不同而配置雷同的方案。报告应展示**帕累托有效方案集合**、明确被支配方案如何淘汰，以及各方案为什么不等价。

### 5.1 多目标、约束优化

形式化：对于有效配置 x，最小化向量 `[quality_loss(x), total_cost(x), p95_latency(x), operational_risk(x)]`，且满足安全/隐私/许可证/准确率下限/设备能力等硬约束。

**Pareto 支配**：如果 A 在所有重要指标不劣于 B，且至少一项严格更好（基于可信的差异），B 可标记为被支配。指标误差/置信区间较大时，不能贸然宣称优越。

对于 n 个节点，每节点 k 个候选，组合数可达 `k^n`。因此先单节点淘汰明显不适配，再保留若干选择，使用分层实验/自适应搜索，并在关键节点组合上进行**端到端回归**。可研究 AgentOpt 的搜索与路由，不盲目复制结论。

## 6. 节点级与工作流级的冲突

示例：一个 OCR 模型在单独扫描件字符识别更好，但返回的结构与旧提取节点不兼容，导致合同最终关键字段准确率下降。因此：

- **Node-level**：评价该节点的输入输出质量、成本、速度、稳定性与格式契约。
- **Workflow-level**：在相同真实业务案例上，评价最终任务成功率、严重错误、延迟、费用、重试、人工处理及链路复杂度。
- **Cross-node effects**：尤其观察输出格式变化、检索召回偏差、长上下文截断、错误累计、缓存污染、并发和上下游错误放大。

即使单节点优势显著，未通过集成测试也不能推荐直接上线。

## 7. 开发测试、预发布与正式生产

### 7.1 开发测试期

目标：快速缩小候选集、最低开销获取足够的决策证据。费用包括测试 API/推理、评判模型/人工标注、样本准备、重跑及工程时间。允许把昂贵强模型作为**少量对照**，不表示未来生产持续使用它。

### 7.2 预发布期

目标：验收全量回归、压力/并发/边界测试、隐私/权限审查、故障注入、缓存与费用预测。输出上线门槛是否满足；未测得的生产 SLA 不可虚构。

### 7.3 生产期

目标：在真实请求量、输入复杂度、峰值流量及故障特征下优化长期 TCO 和稳定性。考虑：

- 生产流量分布与季节波动、峰谷、平均和高分位输入大小；
- API 计费单位、缓存折扣、重试放大、图片/音频/视频价格、批处理与流量套餐；
- 本地 GPU/CPU 服务器折旧或租金、电力、空闲成本、利用率、人员维护；
- 失败后的兜底 API、人工复核/纠错、数据传输、监控、迁移与许可证；
- 区域可用、配额、服务端限速、可观测性、升级风险、灾备。

示例月成本：`C_month = C_API + C_compute + C_storage + C_network + C_ops + C_retries + C_human_review + C_amortized_migration`。本地没有 API 请求费 ≠ 免费；一个按次最便宜的模型也可能因为重试而有最高的合格业务任务成本。

**未知输入**：若生产 QPS/日量、硬件租金和人工纠错率未知，只能做情景估计（低/中/高流量）与敏感性分析，不得给“生产月费精确数”。

## 8. 阶段特化方案集

最终方案应至少回答：

- **开发用哪个方案最快完成可靠验证**（测试预算与实验工具）。
- **上线前需要补充什么证据**（性能、稳定性、边界和风险）。
- **生产选择哪个方案更经济**（不同规模的临界点、硬件和运维、替代提供商）。
- **多节点配置如何组合**（节点级与整条链对比、必要回退/人工复核）。
- **何时应重评**（模型新版本、供应商涨价、输入分布变化、失败率上升、部署条件变化）。

## 9. 输出应允许“不推荐更换”

评测发现现有模型足够好、迁移风险太高、样本太少或者新模型收益低于维护代价时，输出“保留现状”和所需后续实验，是有效结果，不是失败。
