# 01 · 产品愿景、需求与边界

> **性质：经讨论形成的目标与设计假设，不代表已交付功能。**

## 1. 问题从哪里来

最初的 LLM Race 希望收集价格、上下文、能力和榜单，用 MCP 推荐合适的语言模型。扩展到 Model Race 后，范围包括 LLM、图像理解/生成、OCR、ASR、TTS、音频、视频、Embedding、Rerank 等。调研显示 Models.dev、LiteLLM、Hugging Face、Artificial Analysis、Replicate、fal.ai 及其他项目已有各类目录、定价、基准与分发能力。**没有充分理由为了重复数据聚合而经营一个新的通用模型数据库**。

讨论逐渐发现真正尚待解决的用户问题：**开发者已经在 Coding Agent 中构建一个真实项目，应用内部有多个不同的 AI 节点；他需要 Agent 根据当前业务与可用测试样本，自动帮每个节点寻找并比较技术路线，评估节点组合，并考虑开发测试及生产上线不同阶段的经济性。**

项目的独特价值如果存在，应体现为**降低独立工程师完成可信选型所需的人工调研、接入、评测和反复试错成本**，而不是数据量或排行榜。

## 2. 完整产品定义

当用户在代码仓库中调用 Model Race Skill：

1. Agent 读取项目结构、需求和设计文档、API/模型调用、依赖配置、测试、业务样本、运行环境，以及当前开发进度；只访问已授权目录与数据。
2. 自动识别已存在与计划中的 AI 节点，理解每个节点的**业务目的、输入输出契约、上游/下游依赖、失败后果、质量门槛和阶段**。
3. 按节点动态选择评估维度：如速度、任务正确率、P95 延迟、成本、部署、隐私、许可、硬件、噪声数据适应性、并发、鲁棒性、可维护性。不使用僵化的统一权重。
4. 探索**可比较的候选实现方案**：传统规则、PDF 文本层、OCR 引擎、开源权重模型、闭源 API、混合工作流、缓存、路由及人工复核；不强制必须用模型。
5. 从已有真实测试与经许可的公开 Benchmark 中选择合适样本；必要时建议待人工复核的标注、合成异常案例和评测程序。
6. 在授权预算、安全与部署范围内执行实测；留存配置、模型版本、输入分布、样本量、日志摘要、指标定义与结果。
7. 对候选方案进行**节点级验证**，随后用有代表性的节点组合测试**整条工作流的质量、延迟、资源和费用**，避免局部改进使系统变差。
8. 针对研发试验、上线准备、正式生产分别估算开销、故障策略和适用性。
9. 输出**多个经过证据支持的方案**（质量、性价比、延迟、私有化、开放权重、可靠性、混合等）及 Pareto 集，标注各方案适用条件。
10. 默认只提供可复现报告与候选配置；用户授权后可交给 Coding Agent 在开发分支生成变更、回归并准备发布审批。

## 3. 面向谁

**首要用户：** 使用 Codex、Claude Code 等 Coding Agent 开发多模型应用的独立开发者、小团队、AI 产品工程师与应用 FDE。项目可能缺乏专业 ML Eval 工程师，但已积累代码、测试和部分真实案例。

**进一步用户：** 负责文档自动化、教育辅助、语音/视觉工作流、企业自动化、AI SaaS 的技术负责人，需要向业务方说明选型原因、风险与成本。

**可衡量的使用价值：** 相比人工执行相同评测流程，明显减少人工工时；不降低评测正确性，甚至提高覆盖与可复现性；在业务质量门槛下找到总成本/延迟更合适的配置。

## 4. 重要使用场景

### 4.1 ThinkRoom / Research OS

文档加载和解析、观点/证据抽取、选定来源问答、简报、审议/多角色讨论。应特别评测证据可追踪性、引用正确率、幻觉与拒答、结构化输出、文档类型覆盖、节点间错误传播。已经存在的测试和历史案例优先，不能把纯模拟评价当作生产可靠性证明。

### 4.2 ClassMatter / 班主任工作台

自然语言意图理解、授权事实查询、草稿生成、潜在 OCR/语音等工具节点。尤其关注**越权和非授权写入**、敏感学生信息、审批边界、结构化数据契约、教师额外操作成本。公开验证必须使用合成数据；不得把真实学生隐私自动发往云模型或公共评测服务。

### 4.3 企业文档与合同流程

PDF 文本层提取 → OCR/表格处理 → 字段抽取 → 条件判定 → 报告/审批。比较“规则 + 专用 OCR + 小模型”与“大 VLM/强 LLM”等不同方案；客户私有材料需要授权、脱敏或在隔离环境中测试。

### 4.4 语音、视觉与生成业务

本地中文 ASR（WER/CER、实时率、内存）、实时 TTS（自然度、首包延迟）、图像理解（事实精度、分辨率）、生图/视频（遵循度、一致性、单位生成时间和人工质检）等；为**每个任务**选择自己的指标和数据集，不将不兼容分数硬比较。

## 5. 优先级与产品边界

| 项目 | 优先方向 | 明确不做 |
| --- | --- | --- |
| 交互 | Agent 原生调用、少人工操作，提供决策证据 | 为了视觉展示优先做独立 SaaS |
| 对象 | 已存在的项目、多个异构 AI 节点及输入分布 | 只评选“全球综合第一模型” |
| 来源 | 保留来源发现方法、源可信度与许可证信息 | 自建全量模型/Benchmark 数据仓库 |
| 评测 | 调用成熟框架，使用项目实际案例，端到端复核 | 所有 Benchmark 都从零重写 |
| 决策 | 多方案、多目标，开发与生产分别计算 | 单一综合分、统一最佳模型 |
| 执行 | 自动编排、付费/敏感/发布阶段设审批 | 未授权无限调用、生产直改 |
| 扩展 | 可迁移的 Skill + 瘦 Harness | 为通用化而过早做复杂平台 |

## 6. 必须具备的五项核心原则

- **Project-first**：项目业务验收标准权重高于通用榜单。
- **Node-specific**：每个节点独立规定约束与指标，任务和模态不同不能复用错误评测器。
- **Evidence-driven**：第三方宣称、公开基准、本项目实测、推测四种证据等级明确分离。
- **System-aware**：真实决策对象是工作流完成率、总成本与错误风险，不是单节点名次。
- **Evaluation-before-replacement**：先跑评测再提配置变更；默认不操作生产。

## 7. 成功与失败的定义

**成功实例**：在一个从未为此 Skill 专门布置的项目里，用户给出目标和预算后，Agent 能自动识别关键节点、提出具体约束、找到合适测试数据、运行少量受控而真实的候选测试、重现结果并解释至少两个不同取舍的系统方案；经开发者审核，输出可落地且不夸大证据的实施建议。

**失败实例**：Agent 仅仅抓排行榜拼报告；忘记项目输入的噪声分布；把公开榜单成绩当项目准确率；未经许可传播个人/客户信息；评测费用失控；声称测过但实际只查了网页；不测端到端便改动生产；输出一堆没有明确决策意义的指标。

## 8. 术语澄清

- **Model / Task / Modality / Endpoint / Evaluation** 分别代表模型身份、实际任务、输入输出数据模态、服务商部署接口、评测实验；不应混为一谈。
- **开放权重 vs 开源**：提供模型权重不必然等于完整开源；需核查商业使用、再分发和衍生许可。
- **模型选型 vs 技术方案选型**：最佳路径可能是无 AI 的原生解析、规则或人工复核；Model Race 应允许输出“无需模型”。
- **推荐 vs 已证实更优**：只有评测和适用环境支持时才能说“经实测更优”。
