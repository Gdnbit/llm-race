# 06 · 开发路线图、验证实验与验收门禁

> **Roadmap / 尚未执行。** 路线按“研究—最小证据—逐步泛化”组织，不承诺上线日期或假设已有成效。开发中以验收门禁判断是否进入下一阶段。

## 0. 为什么第一版必须收敛

本项目不是再做一个数据聚合平台；它要证明 **Coding Agent + 专业 Skill + 复用现成 Eval 工具** 能够在真实已有项目上，比临时即兴评测更稳妥、低人工成本、可追溯地完成多模型/多节点决策。

**先选择两个真实项目、两个至三个节点、几种明确的候选方案**，再看是否值得扩展到全部模态。项目目标十分广泛，但 MVP 不该一次完成全模态、全模型、全部工具的适配。

## 1. Phase 0：研究与基线审计

**目标**：验证现有成熟工具究竟覆盖哪些能力，确定 Model Race 真正需要新写的部分。

任务：

- 审计本仓库代码/现有文档/现有 CI，留下准确的 shipped vs planned 清单；
- 实际复现 AgentOpt 的多节点 LLM 选择案例、One-Eval 的 Skill 评测工作流、AWS Agent-EvalKit 的项目扫描能力；
- 试跑一种成熟执行框架（例如 EvalScope / Promptfoo / Pydantic Evals / Inspect AI），不要全都引入；
- 查各候选仓库的许可证、依赖维护、插件限制、GPU/API 费用、跨模态输入支持；
- 选择首个实验项目和两个或三个节点；明确每个节点的可验收业务目标；
- 设计与“让 Coding Agent 不加载 Skill 直接完成相同任务”的对照组。

**完成条件**：输出带链接和实际试跑记录的能力矩阵、复用决策、可执行 baseline 命令；明确哪些问题现有组件已解决，哪些尚待开发。

**失败/停止条件**：如果工具组合已满足用户目标且 Skill 没有额外价值，优先做最小脚本/模板，甚至暂停独立产品化。

## 2. Phase 1：ThinkRoom 的最小闭环（推荐首个试验场）

理由：存在文档证据提取、来源约束问答等比较可测的业务节点，已有部分真实项目测试/评测基础。**需要重新检查其当时的最新源码与测试**，不能凭历史对话推定其状态。

建议只做：

- **节点 A**：有确定性输出的观点/证据抽取或结构化结果；
- **节点 B**：选定来源问答或简报生成；
- 可选 **节点 C**：文档解析/OCR（如果项目当前实际已有或待开发、且有合法测试数据），不能凭空当作已上线节点。

基线步骤：

1. Skill 在项目根目录完成只读扫描，列出找到的 AI 节点、代码/配置证据、依赖及疑似未发现的动态节点。
2. 选两个具有真实可比较案例的节点，确认目标、硬约束、评分方法、需要用户授权的步骤。
3. 复用已有测试与标注；若缺真值，说明缺口，准备需人审的候选评测数据。
4. 从可信来源发现候选；**每节点至少保留现状作为 baseline**，再选少量候选（如两到三个）进行试验。
5. 用选定执行框架做 **research-only → 少量真实调用 → 扩大验证**；保留每次模型响应的评价指标、使用/花费、延迟和失败码。
6. 针对少量候选组合执行端到端任务，用现有工作流基线作比较。
7. 输出质量优先、性价比优先、保留现状（必要时再加速度优先）等至少两种**真实不同**方案；如两种方案事实上同一配置，允许合并。
8. 研发费单列，生产费分别给低、中、高请求量情景和敏感性；未知参数必须显式标明。
9. 导出 Markdown 报告 + 机器可读实验记录 + 可选开发分支的配置修改建议；不直接改生产。

**验收条件**：

- 扫描节点均能回溯到代码/文档/Trace；错误识别和漏报有记录；
- 可运行至少一个有明确判定方法的自动评测（不只是网页榜单比较）；
- 每条项目实测结论可回溯到实验 ID、样本来源/版本、评判器与调用记录；
- “质量/速度/成本”相关数字真实，不报未执行的模型分数；
- 方案报告展示当前基线与替代方案，在节点级与端到端对照，不把单节点成绩外推；
- 测试没有越过事先确定的费用、调用数据及生产修改权限；
- 第三方数据与本项目实测明确区分；有失败样本和适用边界；
- 受限或不可靠输入时能输出 `insufficient_evidence`，不会捏造确定性排序。

## 3. Phase 2：迁移到 ClassMatter 验证泛化

目的：检验 Skill 不是给 ThinkRoom 写死的自定义脚本。

建议节点：班主任自然语言意图识别、受控事实检索、结构化草稿输出；如已经存在其他多模态节点，再考虑 OCR/ASR。**当前公开 ClassMatter 不应拿真实学生/健康/心理记录做外部自动评测**；仅用合成或明确合法授权的隔离样本。重点评测越权、未授权副作用、错误事实和人工审核守卫。

成功标准：复用相同 Skill 入口和主要评测流程，通过替换配置、节点发现器和评分规则而非大面积复制业务代码完成至少一个不同项目的评测。对源自 ClassMatter 的隐藏/未完成节点，记录 `planned`，不作为现成 API 评测。

## 4. Phase 3：扩充跨模态与数据源发现

前两阶段通过后再逐类扩展：

| 增量 | 目标 | 必要测试 |
| --- | --- | --- |
| 文档/OCR | PDF 原生文本 / OCR / VLM 混合 | 中文合同/表格/图像质量分层；许可证 |
| ASR/TTS | 离线/实时任务对比 | 中文口音/噪声、RTF、首包/内存、语音授权 |
| 视觉理解 | 图表、图片事实提取、结构化描述 | 视觉误识别、文图一致性、高低分辨率 |
| 图像/音频/视频生成 | 生成效果和单位成本 | 任务遵循、人工盲评、时长/尺寸与计费 |
| Embedding/Rerank | 检索召回与端到端问答 | 检索语料隔离、Recall/NDCG、索引迁移 |

跨模态的最小共享接口是任务输入/输出契约、候选 Provider、任务专用 scorer、请求用量 ledger、结果审计；**不要追求一个统一且虚假的“模型智能分”。**

## 5. Phase 4：系统级组合优化与生产情景建模

- 约束优化：先节点候选硬筛，再逐步搜索合理组合，不暴力枚举海量笛卡尔积；
- 端到端：评测节点输入输出契约变化、依赖、故障级联、路由错误、回退和人工成本；
- 可选**条件式路由**：输入质量/难度判断→低成本主路径→困难例子高质量兜底；必须计入路由器本身成本和误判；
- 生产 TCO：流量情景、峰值、价格版本、GPU/CPU 租金、网络、维护、人工、失败与重试；找到可能存在的业务量成本交叉点；
- 继续只输出**可验证的迁移建议与回滚计划**，不默认替换线上服务。

## 6. Phase 5：Skill 发布与生态验证

确认已经在至少两个性质不同的真实项目上完成可复现评测后：

- 打包 Agent Skills 兼容的 `SKILL.md`、reference、脚本、manifest 和示例合成项目；
- 安装与运行说明面向 Codex/Claude Code，明确各宿主对工作目录、网络、凭据、后台长任务的差异；
- 增加离线夹具与 CI（预算熔断、权限边界、数据泄露检查、契约、报告校验、回归）；
- 更新主 README/English README，清楚标示 stable/experimental、真实能力/环境与局限；
- 公开**匿名合成**实验报告和可运行 Demo；不公开用户/客户资料；
- 以独立开发者真实上手任务验证便利性，不把 Star/安装数视为评测质量保证。

## 8. 衡量项目自身 ROI

与相同任务、相同预算、相同候选和时间条件下的 **Coding Agent 无 Skill 的直接调查** 对照：

- **人工介入**：完成人工确认/调研/测试/解释耗费的人时和操作数。
- **结果有效性**：模型节点查全率、业务约束识别准确性、选用的 Benchmark/指标适用性。
- **评测正确性**：错误评分器、未标注样本伪真值、模型/服务商身份对齐错误、虚假数据、违规费用和数据安全事件。
- **决策价值**：相同质量门槛下每成功任务成本、P95、严重错误和上线准备度的变化。
- **通用性**：是否能适应新项目/新模态而不重新编写大部分代码。
- **报告可复现率**：独立工程师按报告配置重复跑得出的结果是否在合理不确定性内。

具体阈值需在 baseline 后设定；不能预先声称“省 90% 时间”“质量提升 30%”。

## 9. 质量、隐私与工程硬门禁

- [ ] 不读取未授权的数据；本地样本不会被自动送到外部模型。
- [ ] 研究模式零付费调用，实测模式有获授权的硬费用和并发/样本限制。
- [ ] 不触发真实消息发送、支付、写入业务数据库等危险副作用。
- [ ] 数据源许可、模型商业许可、地域和发布条款有记录。
- [ ] 用户案例有代表性/已知偏差/人工真值说明。
- [ ] 每项指标单位、样本量、误差来源、模型版本与实验时间可查。
- [ ] 实验失败或费用不足时生成部分报告并明确 incomplete，而非“成功”。
- [ ] 成本计算覆盖非 Token 单位、开发与生产不同组成。
- [ ] 整条工作流经过足够的回归；无回归时替换建议仅供探索。
- [ ] 文档示例数字标明虚构，公开仓库无 PII、客户数据、密钥、完整私有 Trace。

## 10. 开发交接原则

当在 Codex 开始实现时，请先读取 [目录](README.md)、本路线图、[架构](04-SKILL-ARCHITECTURE.md) 与 [契约示例](07-EXAMPLES-AND-CONTRACTS.md)，**先检查真实代码和环境，不直接假定计划功能存在**。每个阶段提交：修改内容、测试命令及结果、未完成项、用到的外部项目版本/许可证、成本与隐私审查。先小样本形成证据，再扩张产品形态。
